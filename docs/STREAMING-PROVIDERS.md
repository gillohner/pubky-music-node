# Subscription streaming providers: what each one needs

The plug point is `pm_api::streaming::StreamingService` (search, item, stream URL) behind
`/v1/sources/{source}/*`; every source in the table below uses it (seventeen today, from the Internet Archive to Plex). A subscription service
adds an account flow in Settings (OAuth, tokens encrypted in `data_dir`), canonical-ID mapping
(ISRC/MusicBrainz) for favourites and playlists, and an honest quality ceiling in the signal path.
One account per user, never proxied to others (handoff §2). Reverse-engineered APIs only after
legal review.


Every source declares what it can do (`features`: search, play, connect, artists, library, playlists, downloads, lyrics, scrobble) and a stage (`stable`, `beta`, `unofficial`) in `GET /v1/sources`; the Sources tab shows that under "What it does" and offers only those actions.

**Shared apps.** A self-hoster needs no developer credentials except for Spotify. The project's own apps are built in,
but only their public values: the TIDAL and Jamendo client ids and the AcoustID application key, read at build time from
`PM_PROJECT_TIDAL_CLIENT_ID`, `PM_PROJECT_JAMENDO_CLIENT_ID` and `PM_PROJECT_ACOUSTID_KEY` (the release workflow sets
them; the repository holds none). Client secrets never ship. So every sign-in with an app whose secret isn't on the node
is OAuth 2 with PKCE and no secret, and returns through one static page,
`https://gillohner.github.io/pubky-music-auth/callback` ([source](https://github.com/gillohner/pubky-music-auth),
`[auth] return_page` overrides it). The node starts the sign-in with `state = <nonce>.<base64url(its callback URL)>`;
the page sends the browser on to that callback, and the node checks the nonce and redeems the code with its PKCE
verifier, which never leaves it. This works for a node on a LAN with no port forwarding. An app with its secret in the
node config keeps the direct redirect. CI runs `tools/secret-scan.py` over the repository and the built binary.

**Modes.** A service can have an Official mode (its public API) and an Unofficial mode (its private API, may break,
off by default, its own warning and sign-in). Sources › TIDAL holds both behind one **Sign in**: the ways sit side by
side (the official app, the device sign-in tidal-dl-ng uses, your own app), one is picked and remembered, and the status
line says which is in use (STEWARD-CREDENTIALS-REUSE.md). Every source on the Sources page also has an on/off switch:
off hides it from search, Home, item pages and the play order, and keeps its sign-in.

Full-length audio is granted to the **application**, never to the person signing in: no identity scheme
(Pubky, Nostr, a different OAuth account) changes the tier TIDAL assigned to the app, and borrowing another
client's identifiers is the reverse-engineered route this project only takes after legal review. The TIDAL
redirect URI follows the address the browser used when `public_url` is unset (reverse proxies: forward
`X-Forwarded-Proto` and `X-Forwarded-Host`).

What the owner provides: the credentials above, a subscription on the account used for the one
sign-in (run on the test laptop; the browser redirect lands on the node), and a read of the
provider's developer terms, which go into an ADR before the module is written.

What follows once they arrive: the provider module, "Connect …" in both Settings screens with
token refresh on the node, playlist import by canonical URL, the service in the Sources view.

## Beside the sources

- **Last.fm (scrobbling, similar artists):** official API with the owner's own API key and shared secret (Settings › Accounts › Last.fm, or `[lastfm]`, `PM_LASTFM_API_*`); the node ships no key and the secret never leaves it. Plays count like ListenBrainz's (half the track or four minutes; now-playing at the start), wait when Last.fm can't take them, and the session key is a secret in backups. Similar artists show on artist pages, matched to the library.
- **Sign in, the ways side by side** (`GET /v1/sources/{source}/signin`, STEWARD-CREDENTIALS-REUSE.md): a source that signs people in lists its ways, the recommended one first, each labelled by where it comes from (Pubky Music's app, tidal-dl-ng's client, your own app), with a reason when one is not available on this build. `PUT {way}` remembers the pick, `DELETE` signs out of the way in use. The answer names the sign-in in use by user and expiry only, never a token, and `/v1/sources` carries the same one line per source (`sign_in`) for the Sources list. TIDAL, Qobuz, Spotify, YouTube and Last.fm use it.
- **A sign-in from another app on this machine** (`POST /v1/sources/{source}/signin/import {id}` or `{text}`): the node looks in the known places, **read-only**, lists what it found by app, user and expiry (never a token), and uses one on a click; from another machine, the file itself or a paste does the same. What is imported is kept exactly like the node's own sign-in (the same setting, sealed in backups, gone with Sign out) and renewed by the node where the refresh token came from the client this build carries; otherwise it runs until it expires and the tab says so, with the other ways right there. Refused imports (expired, not a token file) change nothing and say why, with **Try another way**. Qobuz token imports check `user/get` and the streaming plan; Last.fm imports require a named `user.getInfo` response. An unreachable service does not replace a working sign-in. Where the node looks for **TIDAL**: tidal-dl-ng `~/.config/tidal_dl_ng/token.json` (or under `$XDG_CONFIG_HOME`; python-tidal's session file, device-flow tokens from the same client as our built-in one, so they renew; PKCE ones run until expiry), beets `~/.config/beets/tidal_token.json` (same format), tidal-dl `~/.tidal-dl.token.json` (base64 JSON; its own client, no renewal here), streamrip `~/.config/streamrip/config.toml` (`[tidal]`; its own client, no renewal here); a bare access token with an optional refresh token on the next line pastes too. **Music Assistant** is on the list and never read: its `settings.json` keeps sign-ins encrypted with MA's own key. The same chooser is on **Qobuz**, **Spotify**, **YouTube** and, under Settings › Accounts, **Last.fm**. Where the node looks: Qobuz in streamrip `~/.config/streamrip/config.toml` (`[qobuz]`: the app values and a token, or the email with the password's MD5, which is what Qobuz's login takes) and qobuz-dl `~/.config/qobuz-dl/config.ini` (`[DEFAULT]`); Last.fm in rescrobbled `~/.config/rescrobbled/config.toml` (`lastfm-key`, `lastfm-secret`, or the files they name) with the session key in `session` beside it (checked with `user.getInfo` before it is kept; mpdscribble keeps a password, not a session, and is not read). Two kinds of file are **never looked for**, only picked or pasted, because they are a different class from a service's token file: librespot's `credentials.json` (a reusable Spotify auth blob; spotifyd, raspotify, go-librespot keep one) goes into the node's librespot system cache as a 0600 copy, and a yt-dlp **cookies file** (a browser session for the person's Google account) becomes `<data>/youtube/cookies.txt` (0600), passed to yt-dlp as `--cookies` on a disposable 0600 working copy. yt-dlp ignores external config files and cannot recreate the saved cookies after Sign out. Netscape headers, flags, expiry and exact YouTube/Google domains are checked, including `#HttpOnly_` rows; this checks the file, while yt-dlp checks whether the service still accepts the cookies during playback. Each goes with Sign out. Deezer ARLs (favourites and library only) are not done.
- **Sign-in fallback:** when the browser can't reach the node after TIDAL's or Spotify's sign-in page (another network, an app that only allows loopback redirects), "Landed on a page that didn't load?" under the Sign in button takes the address that page landed on, and the node finishes the sign-in from it (`POST /v1/sources/{tidal,spotify}/callback {url}`).
- **Announcements** (`POST /v1/zones/{id}/announce`): not a source; a clip or chime interrupts a zone and it comes back where it was. Home Assistant's `media_player.play_media` with `announce: true` uses it.

## Not offered, and why (STEWARD-PLAN step 5)

- **Needs approval first:** Qobuz (requested by email), SoundCloud's official API (access is by application). Both have unofficial modes above instead.
- **Apple Music:** needs a paid developer account, and MusicKit plays in the browser only, never on the node's outputs.
- **No official playback API:** YouTube Music (beyond the embedded player above), Amazon Music, Bandcamp streaming, Mixcloud. The node's rule is no reverse
  engineering. The `qobuz-api` crate is out for the same reason (it scrapes the web player's credentials) and its GPL-3.0
  licence does not fit the node's MIT.

Import format references: [librespot credentials](https://github.com/librespot-org/librespot/blob/dev/core/src/authentication.rs), [yt-dlp cookie format](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/cookies.py), [Last.fm user.getInfo](https://www.last.fm/api/show/user.getInfo). Only the person’s supplied app/session values are reused; the node does not extract bundled credentials from these projects.
